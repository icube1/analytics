# Product & Architecture Roadmap

## 1. Назначение документа

Этот документ описывает целевое развитие Analytics из локального персонального
дашборда в экономичный мультиплатформенный продукт для долгосрочного финансового
планирования.

Основные цели:

- давать полезный результат человеку даже без капитала и брокерского счёта;
- помогать выстроить финансовую устойчивость, а затем двигаться к финансовой
  независимости;
- показывать влияние сегодняшних действий на долгосрочный результат;
- поддерживать web и mobile с единым вычислительным ядром;
- экономно использовать CPU, RAM, диск и сетевой трафик;
- обеспечить безопасное хранение данных нескольких пользователей;
- заложить монетизацию без ухудшения базовой пользы продукта;
- поддерживать отчёты разных банков и брокеров.

Документ фиксирует направление, а не запрещает менять технологии. Любое крупное
решение должно подтверждаться измерениями на реальных сценариях.

## 2. Продуктовые принципы

### 2.1. Польза сейчас, горизонт на годы

Пользователь должен видеть не только далёкую сумму капитала, но и ближайший
практический результат:

- сколько дней или месяцев обязательных расходов уже защищено;
- насколько уменьшилось тело долга;
- сколько будущих процентов удалось избежать;
- какую часть следующего непредвиденного расхода можно покрыть без кредита;
- как регулярный взнос изменил диапазон даты достижения цели;
- какая доля результата создана взносами, а какая — изменением рынка;
- насколько свежи и полны данные, на которых построен прогноз.

Прогнозы показываются диапазоном, а не обещанием одной точной суммы или даты.

### 2.2. Финансовая устойчивость важнее торговли

Продукт не должен мотивировать пользователя чаще совершать сделки или покупать
конкретные инструменты. Прогресс строится вокруг контролируемых действий:

- понимание денежных потоков;
- формирование резервов;
- погашение дорогих долгов;
- регулярность сбережений;
- поддержание реалистичного плана;
- периодическая сверка плана с фактом.

### 2.3. Privacy by design

- Финансовые суммы, названия операций и документы не отправляются в продуктовую
  аналитику.
- Локальный режим должен оставаться полноценным вариантом использования.
- Серверная синхронизация включается явно и объясняет, какие данные передаются.
- Пользователь может экспортировать и удалить свои данные.
- Токены банков и брокеров не включаются в обычные резервные копии.

### 2.4. Локальные и серверные вычисления дополняют друг друга

- Лёгкие расчёты выполняются локально для мгновенного отклика и приватности.
- Тяжёлые расчёты выполняются в Worker/WASM либо на сервере — в зависимости от
  мощности устройства, размера задачи и тарифа.
- Сервер остаётся авторитетным для доступа, тарифов, синхронизации и сохранённых
  результатов.

## 3. Целевая техническая архитектура

```text
gala-soft.ru
└── Astro: лендинг, документация, обучение, SEO, интерактивное демо

app.gala-soft.ru
└── Vite + React SPA
    ├── IndexedDB / локальный кэш
    ├── Web Worker
    └── financial-engine.wasm

api.gala-soft.ru
└── Rust / Axum modular monolith
    ├── authentication
    ├── tenant isolation
    ├── sync API
    ├── broker import
    ├── billing and entitlements
    ├── bounded job workers
    └── native financial engine

Mobile
├── первый этап: Capacitor + web UI
└── дальнейший этап: native UI + Rust bindings

Storage
├── SQLite WAL на одном сервере
├── версионированные резервные копии
└── PostgreSQL при подтверждённом ограничении SQLite
```

### 3.1. Почему Astro только для публичного сайта

Astro хорошо подходит для лендинга, обучающих материалов и SEO: по умолчанию он
отдаёт статический HTML и добавляет JavaScript только интерактивным islands.

Основное приложение является большим связанным интерактивным деревом: формы,
графики, IndexedDB, импорт файлов, сценарии и общий state. В Astro оно превратится
в один большой React island и почти не выиграет в размере или сложности.

### 3.2. Почему Vite + React для приложения

Текущие страницы Next.js — преимущественно статические оболочки, а полезная работа
выполняется клиентскими React-компонентами. Vite позволяет:

- сохранить большую часть существующего UI;
- убрать постоянный Next.js runtime с сервера;
- отдавать приложение напрямую через Nginx;
- удобно подключить Web Workers и WASM;
- лениво загружать вкладки и графики;
- сохранить путь к Capacitor и концептуальную близость к React Native.

### 3.3. Почему не vanilla, Solid или Svelte сейчас

Vanilla HTML/CSS/JS минимизирует framework runtime, но переносит сложность
состояния, форм, lifecycle, accessibility и графиков в самописную инфраструктуру.

Solid и Svelte могут дать компактный UI, но потребуют переписать тысячи строк
компонентов и заменить Recharts. До такого решения нужно сначала убрать
подтверждённые расходы текущей сборки:

- `linkedom` в browser bundle;
- статически импортированные вкладки;
- тяжёлые графики;
- Next.js runtime при отсутствии потребности в SSR.

### 3.4. Rust workspace

```text
crates/
├── financial-domain/  # деньги, даты, ставки, идентификаторы, DTO
├── financial-engine/  # долги, вклады, прогнозы, Monte Carlo, IRR
├── financial-wire/    # версионированные API-контракты
├── financial-wasm/    # wasm-bindgen adapter
├── financial-ffi/     # Swift/Kotlin bindings
└── backend/           # Axum, SQLx, auth, sync, billing, jobs
```

На сервере `financial-engine` подключается как нативная Rust-библиотека. Запускать
собственное доверенное ядро внутри серверного WASM runtime не нужно: это добавит
память, сериализацию и сложность без полезной изоляции.

## 4. Финансовое ядро

В общее ядро переносятся:

- сложный процент и регулярные взносы;
- инфляция, налоги и снятия;
- кредиты и графики погашения;
- срочные вклады;
- портфельная аналитика;
- tracking «план vs факт»;
- live forecast;
- safe withdrawal;
- Monte Carlo;
- расчёт резервов и stress scenarios;
- чистая нормализация брокерских операций.

В ядро не входят:

- React и UI;
- IndexedDB и файловая система;
- HTTP и внешние API;
- локализованное форматирование;
- authentication и billing;
- конкретные парсеры HTML/XLS/PDF.

### 4.1. Числовая модель

Язык и математическую модель нельзя менять одновременно.

Первый Rust-порт повторяет текущую семантику на `f64` и проверяется
дифференциальными тестами TypeScript ↔ Rust. После достижения совместимости
добавлен модуль точных остатков (`lib/money.ts` / `finance_core::money`):

- точные денежные остатки хранятся в минимальных единицах валюты;
- долги, комиссии и налоги получают явно описанные правила округления
  (`halfAwayFromZero`, `halfEven`, `towardZero`) через DTO `moneyRound` /
  `moneyAdd` / `moneyInterest` / `moneyAmortize`;
- текущая разбивка платежа в UI идёт через целочисленные minor units, а
  compound / Monte Carlo остаются на `f64` до отдельной проверки паритета;
- калькулятор считает прогноз, Monte Carlo и поиск безопасного вывода в
  finance Worker; WASM включается только флагом `NEXT_PUBLIC_RUST_COMPOUND_PARITY`;
- вероятностные прогнозы, IRR и волатильность остаются на `f64`;
- даты передаются как явные civil dates без скрытого `new Date()`;
- seed Monte Carlo является частью входного контракта.

### 4.2. WASM

WASM выполняется внутри постоянного Web Worker:

```text
versioned input
  → one coarse WASM call
  → complete result / transferable typed arrays
```

Первоначальные кандидаты:

- Monte Carlo;
- safe withdrawal;
- длинные сценарии;
- обработка больших массивов транзакций;
- ресурсоёмкая нормализация импортов.

Ограничения:

- не делать вызов JS ↔ WASM на каждом месяце или операции;
- не блокировать main thread;
- лениво загружать WASM только при необходимости;
- ограничивать число симуляций, горизонт и worker count;
- учитывать батарею и нагрев мобильного устройства;
- иметь TypeScript/server fallback;
- не хранить проверку premium-доступа только в клиенте.

SIMD, shared-memory threads и несколько WASM workers добавляются только после
профилирования. Базовый вариант — один однопоточный Worker.

## 5. Путь пользователя к финансовой независимости

Путь не должен быть жёсткой лестницей. Пользователь выбирает приоритеты, а система
объясняет последствия.

### Этап 0. Точка старта

- быстрый ручной ввод без обязательной регистрации;
- доход, обязательные расходы, долги, текущие резервы;
- импорт выписки как необязательное улучшение точности;
- первый результат за несколько действий.

### Этап 1. Контроль денежных потоков

- объяснённая доля расходов;
- регулярные обязательства;
- свободный денежный поток;
- предстоящие крупные платежи;
- качество и свежесть данных.

### Этап 2. Базовая защита

- минимальный ликвидный резерв;
- отсутствие просроченных обязательств;
- покрытие ближайших обязательных платежей;
- план действий при кратком падении дохода.

### Этап 3. Работа с долгами

- остаток тела и будущие проценты;
- дорогие и дешёвые долги рассматриваются раздельно;
- сравнение ускоренного погашения и сохранения ликвидности;
- сценарии потери дохода при продолжающихся платежах;
- отсутствие универсального совета «сначала погасить всё».

### Этап 4. Устойчивая система резервов

- emergency fund;
- фонды ожидаемых нерегулярных расходов;
- семейные риски;
- выбранные пользователем цели и впечатления.

### Этап 5. Регулярное накопление

- автоматизируемый взнос;
- устойчивость взноса, а не максимальная сумма любой ценой;
- вклад пользователя отдельно от доходности рынка;
- влияние изменения взноса на диапазон достижения цели.

### Этап 6. Рост капитала

- диверсификация и концентрация как факты;
- покрытие капиталом части годовых расходов;
- сценарии инфляции и изменения дохода;
- промежуточные milestones.

### Этап 7. Финансовая независимость

- диапазон возможных дат;
- консервативный, базовый и оптимистичный сценарии;
- безопасное снятие;
- защита от sequence-of-returns risk;
- периодическая проверка предположений.

## 6. Подушка безопасности и система резервов

Одна фиксированная «подушка на N месяцев» не подходит всем. Продукт должен
моделировать несколько слоёв ликвидности и разные жизненные ситуации.

### 6.1. Слои резервов

1. **Операционный остаток**
   - ближайшие обязательные платежи;
   - защита от кассового разрыва до следующего дохода.

2. **Стартовая подушка**
   - небольшой быстро доступный резерв;
   - особенно важен до ускоренного погашения долгов.

3. **Основная подушка**
   - потеря дохода;
   - болезнь;
   - срочный ремонт;
   - незапланированный переезд;
   - помощь близким.

4. **Расширенный резерв**
   - нестабильный или сезонный доход;
   - длительный поиск работы;
   - единственный источник дохода в семье;
   - высокая стоимость медицинских или семейных рисков.

5. **Sinking funds**
   - предсказуемые, но нерегулярные расходы;
   - ремонт машины и жилья;
   - страховки, налоги, обучение;
   - техника, животные, ежегодные платежи.

6. **Фонд впечатлений**
   - путешествия;
   - праздники;
   - хобби;
   - семейные события;
   - другие важные для качества жизни цели.

Фонд впечатлений не является чрезвычайным резервом. Его нужно планировать
отдельно, чтобы долгосрочная стратегия не требовала «отложить жизнь на потом».

### 6.2. Персонализация целевого размера

Диапазон резерва зависит от:

- обязательных месячных расходов;
- стабильности и числа источников дохода;
- времени поиска работы в профессии;
- числа иждивенцев;
- наличия второго дохода в семье;
- долговой нагрузки и фиксированных платежей;
- состояния здоровья и страхового покрытия;
- ликвидности остальных активов;
- предстоящих жизненных событий;
- допустимого уровня риска пользователя.

Приложение показывает диапазон и факторы, которые его изменяют. Пользователь
может изменить предположения.

### 6.3. Резерв при наличии долгов

Нужно сравнивать стратегии, а не выдавать единый ответ:

- минимальная подушка + ускоренное погашение дорогого долга;
- более крупный резерв при нестабильном доходе;
- сохранение ликвидности при больших обязательных платежах;
- частичное досрочное погашение;
- стресс-тест нового кредита после непредвиденного расхода.

Интерфейс показывает:

- проценты, которые можно сэкономить;
- риск снова воспользоваться кредитом при отсутствии резерва;
- сколько месяцев платежей покрыто;
- результат при временной потере дохода.

### 6.4. Стабильная ситуация

При стабильном доходе продукт не заставляет бесконечно увеличивать cash reserve.
После достижения выбранного диапазона новые свободные средства распределяются
между:

- долгосрочными целями;
- инвестиционным планом;
- sinking funds;
- впечатлениями;
- досрочным погашением долгов.

### 6.5. Семья

Household-модель должна поддерживать:

- общие и личные счета;
- нескольких взрослых с разными правами доступа;
- детей и других иждивенцев;
- один или несколько источников дохода;
- декрет, уход за родственником и временную потерю одного дохода;
- семейные цели и личные цели каждого участника;
- образование, здоровье и крупные семейные события;
- отдельные приватные категории, не раскрываемые другому участнику.

Семейные stress scenarios:

- один доход исчезает;
- одновременно возникает крупный медицинский расход;
- ремонт жилья или автомобиля;
- незапланированный переезд;
- рост обязательных расходов;
- использование подушки с последующим планом восстановления.

Использование подушки по назначению считается успешной работой системы, а не
потерей прогресса.

## 7. Геймификация без вредных механик

### 7.1. Полезные механики

- карта финансовой устойчивости с несколькими маршрутами;
- маленькие добровольные missions;
- immediate feedback после действия;
- мягкая регулярность: «3 проверки за 4 недели»;
- milestones по runway, долгу и покрытию расходов;
- сценарий «что изменилось с прошлого месяца»;
- privacy-safe карточки достижений без абсолютных сумм;
- возможность полностью отключить геймификацию.

Примеры обратной связи:

- «Резерв вырос с 18 до 23 дней обязательных расходов».
- «Погашение уменьшило будущие проценты на выбранном сценарии».
- «Теперь покрываются два из трёх выбранных стресс-событий».
- «Регулярный взнос сдвинул диапазон цели, но результат зависит от доходности».

### 7.2. Запрещённые или нежелательные механики

- fragile daily streaks;
- штраф или стыд за пропуск;
- leaderboard по капиталу и доходности;
- награда за количество сделок;
- стимулирование покупки конкретной бумаги;
- confetti за ежедневный рост рынка;
- скрытые preselected choices;
- urgency, loot boxes и near-miss mechanics;
- продажа доступа к базовой финансовой безопасности.

### 7.3. North Star Metric

Доля активных пользователей, которые за выбранный период улучшили или сохранили
хотя бы один подтверждённый показатель финансовой устойчивости:

- runway;
- отсутствие просрочки;
- снижение дорогого долга;
- регулярность посильного взноса;
- актуальность плана;
- покрытие выбранного stress scenario.

## 8. Импорт брокерских отчётов

### 8.1. Общая модель адаптеров

```text
file / API
  → type and format detection
  → broker adapter
  → normalized ledger
  → reconciliation
  → preview and warnings
  → user confirmation
  → persistence
```

Каждый адаптер возвращает:

- broker и account reference;
- версию адаптера и fingerprint формата;
- позиции;
- сделки и даты расчётов;
- движения денег;
- дивиденды и купоны;
- налоги и комиссии;
- corporate actions;
- coverage по разделам;
- warnings;
- reconciliation с итогами самого брокера.

Неизвестные поля и расхождения нельзя молча заменять нулями.

### 8.2. Приоритет поддержки

1. Сбер — текущий HTML, затем дополнительные варианты.
2. Т‑Банк — XLSX и официальный Invest API.
3. ВТБ — XLS/XLSX, включая разные поколения отчёта.
4. Альфа — XML.
5. Финам — XML и официальный API.
6. БКС — XLS, PDF как fallback.
7. Газпромбанк — после получения реальных samples.
8. Открытие — только legacy-история.

PDF используется только при отсутствии структурированного формата. XLS/XLSX, XML
и API легче валидировать и надёжно сверять.

### 8.3. Реальные тестовые отчёты

Для разработки важен не размер вложенной суммы, а набор операций. Не нужно
рисковать значительными деньгами ради fixtures.

Минимальный полезный набор:

- пустой новый счёт;
- пополнение и вывод;
- покупка и продажа;
- комиссия;
- незавершённый T+1 расчёт;
- акция;
- облигация с НКД и купоном;
- дивиденд;
- удержанный налог;
- иностранная валюта, если доступна;
- перевод между счетами;
- закрытая позиция;
- отчёт через границу года.

Для каждого файлового адаптера желательно иметь 3–5 отчётов разных периодов и
версий. Один самостоятельно созданный счёт не покроет все edge cases, поэтому
дальше потребуется программа добровольного предоставления обезличенных fixtures.

Перед добавлением в репозиторий автоматический sanitizer удаляет:

- ФИО;
- номер договора и счёта;
- подписи и изображения;
- адреса, телефоны и e-mail;
- налоговые идентификаторы;
- уникальные персональные reference;
- метаданные документа.

После sanitization должна сохраняться внутренняя арифметическая согласованность.

### 8.4. Security импорта

- лимит размера файла и распакованного ZIP;
- запрет XML external entities;
- ограничение глубины XML;
- игнорирование macros, formulas и external links в spreadsheets;
- запрет прямого отображения импортированного HTML;
- parsing в Worker (клиентский broker Worker) или изолированном server job;
- явное подтверждение неполного импорта;
- хранение source provenance для каждой операции.

## 9. Данные, пользователи и синхронизация

### 9.1. Начальная серверная модель

SQLite WAL:

- `users`;
- `households`;
- `household_members`;
- `devices`;
- `portfolio_documents`;
- `statements`;
- `broker_accounts`;
- `broker_imports`;
- `ledger_entries`;
- `scenarios`;
- `calculation_jobs`;
- `calculation_results`;
- `subscriptions`;
- `entitlements`;
- `billing_events`;
- `usage_events`.

Все tenant-owned таблицы содержат `tenant_id` или `household_id`, revision и
timestamps. Уникальные индексы также включают tenant identifier.

### 9.2. Sync

- клиент хранит локальную копию и последнюю revision;
- сервер отдаёт изменения после revision;
- mutation содержит base revision и idempotency key;
- конфликт возвращает `409`, а не молча перезаписывает данные;
- удаление представляется tombstone;
- export/import остаётся версионированным публичным контрактом.

### 9.3. Когда переходить на PostgreSQL

Не по числу регистраций, а при появлении измеряемых ограничений:

- рост lock wait;
- ухудшение write latency;
- необходимость нескольких API instances;
- сложные конкурентные billing transactions;
- превышение допустимого окна backup/restore;
- потребность в row-level security как дополнительном барьере.

## 10. Экономное выполнение задач

На сервере используется bounded job pool:

- ограниченное число workers;
- per-user concurrency;
- max execution time;
- cancellation;
- bounded retries;
- dead-letter state;
- idempotency key;
- кэш по версии engine и хэшу input;
- дедупликация одинаковых расчётов;
- приоритет интерактивных задач над фоновыми.

Redis, Kafka и Temporal не добавляются до появления требований, которые SQLite
или PostgreSQL job table не покрывает.

Решение local/server принимается по policy:

- размер задачи;
- характеристики устройства;
- online/offline status;
- battery-saving preference;
- тариф;
- наличие результата в кэше.

## 11. Монетизация

Billing интегрируется через provider-neutral interface:

```text
BillingProvider
├── create_checkout
├── open_customer_portal
├── verify_webhook
├── cancel_subscription
└── fetch_subscription_state
```

Возможные провайдеры выбираются позднее с учётом юрисдикции и доступности.

Webhook:

- проверяет подпись по raw body;
- дедуплицируется по provider event ID;
- допускает повтор и нарушение порядка событий;
- транзакционно обновляет entitlement;
- регулярно сверяется с состоянием провайдера.

### Возможное разделение тарифов

**Free**

- ручной baseline;
- система резервов и baby steps;
- базовые сценарии;
- локальное хранение;
- один портфель;
- экспорт данных.

**Pro**

- облачная синхронизация;
- несколько устройств;
- multi-broker import;
- расширенная история;
- тяжёлые сценарии и Monte Carlo;
- автоматические отчёты;
- уведомления;
- дополнительные stress tests.

**Household**

- семейное пространство;
- роли и приватные категории;
- общие цели;
- сценарии потери одного дохода;
- совместные резервы и планы.

Доход продукта не должен зависеть от AUM, количества сделок или продвижения
конкретных финансовых инструментов.

## 12. Аналитика и capacity planning

### 12.1. Server metrics

- idle/peak RSS;
- CPU time на route и job type;
- API latency p50/p95/p99;
- event-loop или scheduler delay;
- job queue depth и wait time;
- DB query time и lock wait;
- bytes stored per tenant;
- backup size и restore duration;
- cache hit rate;
- import duration и reconciliation failures;
- error, timeout и restart rate.

### 12.2. Client metrics

- LCP, INP, CLS, TTFB;
- initial JS/CSS transfer;
- main-thread long tasks;
- IndexedDB latency;
- import duration;
- WASM initialization и execution time;
- Worker cancellation;
- sync success и conflict rate.

### 12.3. Product metrics

- time to first useful insight;
- baseline completion;
- созданный пользователем resilience goal;
- weekly/monthly review retention;
- forecast freshness;
- доля объяснённого cash flow;
- улучшение runway;
- снижение дорогого долга;
- достижение milestones;
- использование семейных сценариев;
- conversion и churn без финансовых payload.

### 12.4. Лёгкий monitoring stack

Пока сервер мал:

- structured Nginx logs с request/upstream time;
- JSON application events;
- systemd/cgroup metrics;
- периодическая агрегация в отдельную SQLite DB;
- статический внутренний dashboard на `metrics` subdomain;
- authentication и запрет публичной индексации.

Полный Grafana/Prometheus stack добавляется только при доказанной необходимости.

## 13. Этапы реализации

### Phase 0. Безопасность и сохранение эталона

- закрыть или временно отключить публичные mutation API;
- добавить authentication boundary;
- ограничить размеры запросов;
- перестать запускать приложение от root;
- удалить персональные данные из fixtures и истории репозитория;
- создать обезличенный corpus расчётов и импортов;
- зафиксировать версии схем, даты, timezone, seed и rounding rules.

### Phase 1. Baseline и быстрые улучшения

- server/client/product metrics;
- bundle-size budgets;
- Lighthouse и load scenarios;
- убрать `linkedom` из browser graph (клиент: `DOMParser`; Node: `linkedom` через server-only polyfill);
- lazy-load вкладки и графики;
- измерить TypeScript calculations в Worker.

### Phase 2. Rust financial core

- civil dates и exact money types;
- debt и deposits;
- deterministic compound path;
- taxes, withdrawals и IRR;
- Monte Carlo последним;
- differential и property tests;
- native, WASM и mobile target tests.

### Phase 3. Static web application

- вынести активные API из Next.js;
- перенести UI на Vite React;
- настроить route/tab splitting;
- отдавать assets напрямую через Nginx;
- отключить Next runtime после parity verification.

### Phase 4. Multi-user backend

- Axum modular monolith;
- SQLite WAL migrations;
- users, sessions, tenants и households;
- revision-based sync;
- bounded jobs;
- encrypted backup and restore drills;
- audit trail.

### Phase 5. Resilience journey

- быстрый zero-capital onboarding;
- персонализированная система резервов;
- debt/reserve trade-off;
- family stress scenarios;
- sinking funds и фонд впечатлений;
- milestones и immediate feedback;
- ethical retention loops.

### Phase 6. Broker adapter platform

- строгий Sber adapter;
- общий tabular/XML layer;
- T‑Bank и ВТБ (CSV/text export, sanitized fixtures);
- Альфа и Финам (XML fixtures);
- БКС tabular;
- reconciliation dashboard;
- fixture contribution и sanitization pipeline;
- UI загрузки принимает HTML/CSV/TSV/XML и показывает сверку импорта;
- разбор HTML/CSV/XML идёт в broker Worker, с синхронным fallback.

Двоичный Excel `.xlsx`/`.xls` по-прежнему требует живой образец: текущие
адаптеры принимают текстовый CSV/TSV/XML с теми же идентификаторами.

### Phase 7. Mobile

- Capacitor/PWA validation;
- offline-first storage;
- background sync;
- secure token storage;
- native Rust bindings при подтверждённой необходимости;
- mobile performance и battery budgets.

### Phase 8. Monetization

- entitlement service;
- provider-neutral billing;
- idempotent webhooks;
- Free / Pro / Household;
- usage metering без финансовых данных;
- conversion experiments с guardrails.

### Phase 9. Scale by evidence

- PostgreSQL при ограничении SQLite;
- отдельный worker process при влиянии jobs на API latency;
- SIMD/threads при доказанном выигрыше;
- object storage при существенном росте документов;
- горизонтальное масштабирование только после исчерпания оптимизации одного узла.

## 14. Ближайшие проверяемые решения

1. Может ли Vite React сохранить функциональный parity при существенно меньшем
   client/runtime footprint?
2. Устраняет ли TypeScript Worker UI blocking без Rust-порта?
3. Даёт ли Rust/WASM существенное ускорение на реальных 10–50-летних сценариях?
4. Какой фактический объём данных создаёт один активный пользователь и household?
5. Какова стоимость одного Monte Carlo и одного полного импорта?
6. Где находится предел SQLite WAL на реальном write profile?
7. Какие broker formats дают надёжную reconciliation без PDF?
8. Какие resilience milestones действительно возвращают пользователя без давления
   и стыда?

Ответы фиксируются измерениями и используются для обновления этого roadmap.
